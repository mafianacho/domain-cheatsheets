# 치트시트 작성 규칙 (FORMAT)

사람은 GitHub에서 한 페이지로 읽고, AI 에이전트는 [MCP 서버](../mcp-server/README.md)로 같은 파일을 읽습니다.
그래서 모든 치트시트는 아래 형식을 지킵니다. 형식이 틀리면 `npm run check`가 실패합니다.

## 원칙

1. **한 도메인 = 파일 하나.** `cheatsheets/<id>.md` 하나에 그 도메인의 모든 용어를 담습니다. 하위 폴더나 용어별 페이지를 만들지 않습니다.
2. **용어 하나 = 말 한마디.** 사용자가 AI에게 그대로 말할 수 있는 이름, 한 줄 정의, 실제 요청 문장을 꼭 붙입니다.
3. **그림으로 먼저.** 눈으로 구분되는 용어는 `assets/<id>/` 아래 그림을 붙입니다.
4. **양방향 싱크업.** 사용자는 정확한 단어로 요청하고, AI는 `확인 질문`으로 빠진 정보를 되묻습니다.
5. **전문 분야는 판단을 대신하지 않습니다.** 법·회계·건설 같은 분야는 용어를 이해하고 전문가나 AI와 대화하기 위한 참고용입니다. 시트 첫머리에 이 점을 적습니다.

## 파일 구조

```markdown
---
id: ui-design                 # 파일 이름과 같아야 함 (영문 소문자, 하이픈)
title: UI 디자인               # 한국어 이름
title_en: UI Design           # 영어 이름
summary: 화면 구성을 AI에게 말로 설명할 때 쓰는 레이아웃·컴포넌트·효과 용어
tags: [tech, design, web]     # 첫 태그 = README 분류 (tech | profession)
updated: 2026-11-01
video:                        # (선택) 이 시트 전체 해설 YouTube 링크
---

- **정의**: 첫 화면 맨 위를 크게 차지하는 대표 영역. 큰 제목·한 줄 설명·핵심 버튼이 들어간다.
- **AI에게 이렇게**: "랜딩 페이지 맨 위에 큰 제목, 부제, '무료로 시작' 버튼이 있는 히어로 섹션을 만들어줘"
- **언제**: 서비스 소개 페이지, 제품 출시 페이지의 첫인상
```

## 용어 필드

| 필드 | 필수 | 뜻 |
|---|:-:|---|
| `정의` | ✓ | 모르는 사람도 이해하는 한두 문장 |
| `AI에게 이렇게` | ✓ | 사용자가 복사해서 AI에게 바로 보낼 수 있는 요청 문장 |
| `언제` |  | 쓰는 상황 |
| `헷갈림` |  | 비슷하지만 다른 용어와 차이 |
| `관련` |  | 함께 쓰는 용어 (쉼표로 구분) |
| `확인 질문` |  | AI가 작업 전에 사용자에게 되물어야 할 것 |
| `영상` |  | 해당 용어 구간의 YouTube 링크 (`?t=초`) |
| `근거` | 조건부 | 숫자·기한·조문의 근거. `[법령명 제N조](https://www.law.go.kr/...)`, `[국세청 안내](https://www.nts.go.kr/...)`처럼 https 공식 출처 링크 1개 이상 |
| `검증일` | 조건부 | 근거를 마지막으로 원출처에서 확인한 날 `YYYY-MM-DD` (미래 날짜 불가) |
| `원본` |  | 다른 시트에 원본이 있는 용어일 때, 그 용어로 가는 링크 1개 (아래 '겹치는 용어') |

- 필드는 `- **이름**: 값` 한 줄로 씁니다. 다른 이름의 필드는 오류입니다.
- `근거`와 `검증일`은 항상 함께 씁니다. `korea` 태그 시트(법·회계·건설 등)에서 `정의`·`언제`·`헷갈림`에 숫자+단위(%, 년, 개월, 일, 주, 시간, 원, 억, ㎡)나 `제N조`가 나오면 둘 다 필수입니다(`npm run check`가 검사). 예시 금액만 들어간 `AI에게 이렇게`·`확인 질문`은 대상이 아닙니다.
- 용어 ID는 영어 이름에서 자동으로 만듭니다 (`Hero Section` → `hero-section`). 한 시트 안에서 겹치면 오류입니다.
- 그림은 용어의 첫 번째 `<img>` 또는 `![]()`이며 `../assets/<id>/` 아래에 있어야 합니다.
- `## 이렇게 쓰세요`처럼 용어가 아닌 구역에는 `###`를 쓰지 않습니다. `###`는 모두 용어로 읽습니다.

## 겹치는 용어 (원본 1곳)

같은 용어를 여러 시트에서 설명하면 한쪽만 고쳐져 내용이 어긋납니다. 한 시트를 원본으로 두고, 다른 시트에는 짧은 정의와 원본 링크만 남깁니다.

```markdown
### Stagger Animation · 스태거 애니메이션

- **정의**: 여러 요소가 조금씩 시차를 두고 차례로 움직이는 효과.
- **원본**: [모션 디자인 · Stagger](motion-design.md#stagger--스태거)
```

- 참조 용어에는 `정의`와 `원본`만 쓰고 그림은 넣지 않습니다(그림은 원본에).
- MCP 검색 결과에는 원본만 나오고, `get_term`으로 참조 용어를 찾으면 원본 카드를 돌려줍니다.
- 같은 이름의 용어가 두 시트에 원본으로 있으면 `npm run check`가 실패합니다.

## 그림 규칙

자세한 내용은 [MEDIA.md](MEDIA.md)를 보세요.

- 이해를 돕는 그림을 되도록 모든 용어에 넣습니다. 추상 개념도 비교·흐름·순서도로 그릴 수 있습니다.
- SVG 권장. 크기 `viewBox="0 0 320 200"`, 어두운 카드 배경, 강조색 1~2개. 그림 안 글자는 한국어로 씁니다.
- 축척·층 순서·시간 순서처럼 사실을 나타내는 도식은 실제 비율과 순서를 지킵니다. 다 담을 수 없으면 그림을 나눕니다.
- `<script>`, 이벤트 속성(`onload=` 등), 외부 링크는 넣지 않습니다. CSS 애니메이션은 허용합니다(모션·효과 용어). 움직임을 꺼도 뜻이 통해야 하고 `prefers-reduced-motion` 규칙이 필요합니다.
- 남의 이미지·스크린샷을 그대로 가져오지 않습니다. 직접 그린 그림만 올립니다.

## 새 도메인 추가 순서

1. [TEMPLATE.md](TEMPLATE.md)를 `cheatsheets/<id>.md`로 복사
2. 용어 작성, 그림은 `assets/<id>/`
3. `cd mcp-server && npm ci && npm run generate && npm run previews && npm run check` (`previews`는 Chrome/Chromium이 필요하며, 없으면 `CHROME_BIN`으로 경로 지정)
4. PR
